## 1. 核心原则

1. 只有一套结构驱动的统一算法，不按 case、模块名、文件名、自动 cell 名或固定向量分派。
2. B 负责生产实现，A 负责证明与独立验收；作者不得批准自己的生产变更。
3. A 审计失败时只交反例、证据和 `BLOCKED`，不得直接替 B 修改生产代码。
4. B 不得修改 A 的验收 oracle、放宽证明条件或把证明逻辑复制到 `pass/`。
5. 两人中任一人不可用时，需要交叉批准的工作保持 `BLOCKED`，不得以“人员缩减”为由自审自批。
6. 已经由原 C 独立验收的历史提交，其证据继续有效；新的生产提交必须由当前 A 重新独立验收。

## 5. 双人工作流

1. **冻结输入**：两人确认起点提交、官方 RTL 哈希、工具提交和工作树清洁。
2. **A 冻结证明契约**：明确结构前提、证明义务、预算、结果和拒绝原因；B 书面复核消费者可实现性。
3. **B 实现候选**：在独立分支完成生产变更、自测和可复现证据，不改 A 的 oracle。
4. **A 独立审计**：只针对 B 的完整提交哈希运行静态审计、行为变异、负例、预算和只读指纹检查。
5. **阻塞循环**：A 给出 `BLOCKED` 时，B 在新提交修复；A 对新的完整哈希重新审计。旧授权不得沿用。
6. **A 最终验收**：只有审计 `AUTHORIZED` 后，A 才运行四例、微测试、1000 固定种子、资源/时间/内存和 whole-design EQY。
7. **合并/默认启用**：全部门禁 PASS 后，由 B 做机械合并或默认开关变更；A 对最终合并提交再做差异核对和必要的短回归。未经此步不得宣告 release。

## 6. 授权状态机

```text
B_CANDIDATE
  -> A_AUDIT_BLOCKED -> B_FIX -> A_REAUDIT
  -> A_AUDIT_AUTHORIZED -> A_FINAL_ACCEPTANCE
  -> A_FINAL_BLOCKED -> B_FIX -> A_REAUDIT
  -> G3_PASS -> B_MECHANICAL_MERGE -> A_FINAL_DIFF_CHECK
```

授权只绑定被审计的完整提交哈希；父提交、后继提交、cherry-pick 后内容不同的提交和工作树修改均不继承授权。

## 7. G3 通过条件

技术门槛保持七项不变：微测试全部通过；至少 1000 个固定种子全部 EQY；四个官方 case 全部 whole-design EQY；四例 LUT 不增加且至少一例降低；DFF/IO 等非目标资源不增加；CPU/ABC 时间/峰值内存记录完整；不存在身份或源码位置硬编码。

双人制另外要求：

- B 的生产提交获得 A 对精确哈希的 `AUTHORIZED`；
- 最终 gate、EQY 和计数由 A 独立重新生成，不直接采用 B 的 PASS 文件；
- B 未修改验收 oracle，A 未修改被验收生产代码；
- 接口变更有双方确认；
- 最终合并提交与已验收内容一致。

## 8. 紧急与缺员规则

双人制不设置“临时兼任即可自批”的例外。若 A 无法验收，B 的候选可以继续开发但状态只能是 `UNVERIFIED`；若 B 无法修复，A 只能保留 `BLOCKED` 和反例。若必须由同一人临时跨界修改，须拆成独立提交并等待另一人恢复后复核，期间不得默认启用、合并发布或宣告 G3 PASS。
