## 3. 冻结的模块接口

### 3.1 A 接收的入口请求 `EntryRequest`

每次请求只代表一个 `$mux.A/B` 或 `$pmux.A/Bi` 数据入口，至少包含：

- 模块稳定标识；
- 目标 cell 稳定标识和只读引用；
- 物理端口 `A/B`；
- `$pmux.Bi` 的分支编号、物理端口起始位和宽度；
- 原始数据入口 `SigSpec`；
- 由 B 按规范生成的初始 guard 事实；
- 原端口快照标识；
- 固定预算：512 cell、8192 规范化信号位、262144 队列事件。

A 必须重新校验 guard 的结构合法性，但不得自行扩大 guard：

- `$mux.A`：`S=0`；
- `$mux.B`：`S=1`；
- `$pmux.A`：全部 `Sj=0`；
- `$pmux.Bi`：仅 `Si=1`。

### 3.2 A 返回的分析结果 `EntryAnalysisResult`

结果至少包含：

- 入口状态：正常、`fact_conflict`、预算耗尽或请求非法；
- 每个原本非常量目标位的结论：证明为0、证明为1或未知；
- 每个确定结论对应的证明编号；
- 证明记录表：目标位、值、规则、直接前提、来源cell和父证明编号；
- 使用的 cell、规范化位和队列事件计数；
- 每个未知位的稳定原因码。

预算耗尽时，已经具有完整证明的位可以保留；尚未完成的位统一返回未知。`fact_conflict` 必须使当前入口的全部确定位失效。

### 3.3 B 生成的端口计划 `PortRewritePlan`

B 先按数据入口接收 A 的结果，再按 `(module, cell, physical_port)` 合并，至少记录：

- 原端口完整快照和位宽；
- 每个待替换物理位的原值、目标常量、来源入口和证明编号；
- `$pmux.B` 位到分支编号及分支内位号的映射；
- 相同目标去重记录；
- `rewrite_conflict` 及被放弃入口；
- 稳定提交顺序和诊断计数。

同一物理位的目标相同则去重；目标不同则放弃涉及该位的数据入口。不同 cell 之间即使存在数据依赖也不视为冲突。

## 4. 三人的具体任务与交付物

### 4.1 A：证明引擎负责人

任务：

1. 建立 `SigMap` 后的逐位事实表，事实仅有 `UNKNOWN/ZERO/ONE`。
2. 建立确定性工作队列和稳定编号。
3. 实现直接连接、NOT、AND、OR、受限 `$logic_*`、受限 `$reduce_*`、已知选择 `$mux` 的冻结传播规则。
4. 实现严格的 `$eq/$ne` 常量反推，只接受位宽、符号和扩展明确的情形。
5. 使用 `ConstEval` 做正向求值，自定义代码做反向传播、guard注入和证明记录。
6. 执行三项硬预算，并输出稳定原因码和计数。
7. 保证相同输入设计和相同请求产生完全一致的结果和证明选择。

交付物：

- 证明引擎源文件；
- 共享接口实现；
- 规则级最小测试数据或测试需求清单，交给 C 纳入统一测试；
- 支持的 cell/规则表和拒绝原因码表；
- 不修改 RTLIL 的检查证据。

A 完成标准：接口编译通过；所有冻结规则均有正反例；无任何网表写操作；预算和证明链可复现。

### 4.2 B：Pass、改写与集成负责人

任务：

1. 遍历当前 selection 中全部合法 `$mux/$pmux`，生成稳定入口顺序。
2. 校验端口、宽度、分支切片和可修改性。
3. 严格生成四类局部 guard，不累积外层 MUX 路径。
4. 通过共享接口调用 A；开发初期使用固定桩结果，不自行实现证明。
5. 过滤原常量和 `x/z`，建立逐入口结果，再合并为 `PortRewritePlan`。
6. 处理去重、`rewrite_conflict`、全批快照预检查和一次性原子提交。
7. 保证只修改计划中的 `A/B` 端口位，不修改数据源、`S/Y`、参数、分支数和时序结构。
8. 输出规范要求的统计、原因码、时间和内存信息。
9. 注册 Pass，并按冻结插入点接入 `synth_intel`；Pass 后显式调用 `opt_clean`。
10. 负责 A、B、C 三方成果的机械集成和构建问题，不得以集成为理由改变算法。

交付物：

- Pass入口、枚举器、guard构造器、计划器和提交器；
- 可替换的分析器桩，供 A 完成前联调；
- 插入 `synth_intel` 的最小补丁；
- 日志字段与退出状态说明；
- 全批预检查失败时“零写入”的证据。

B 完成标准：使用桩结果可以精确改写指定端口位；多分支 `$pmux.B` 合并无覆盖；任一快照不一致时全批零写入。

### 4.3 C：验证与评测负责人

任务：

1. 把规范中的16类测试分别做成独立、最小、可复现用例。
2. 为每例定义是否应触发、目标 cell/端口/位、预期原因码和 EQY 结果。
3. 建立统一测试入口，依次执行结构检查、Yosys `check`、EQY、统计核对。
4. 建立固定种子随机 MUX/PMUX 设计生成器，支持100例快速回归和1000例阶段验收。
5. 复用官方基线流程，比较四个 case 的 LUT、DFF、IO、CPU时间和峰值内存。
6. 检查新增cell为0、仅计划中的 `A/B` 位变化、`S/Y`与参数不变、原 `x/z`不变。
7. 保存失败种子、命令、工具版本、日志和最小化前的失败设计。
8. 输出机器可读结果和人工汇总；不得把“替换位成功”报告为“LUT优化成功”。

交付物：

- 16类微型测试及期望清单；
- 100/1000例随机测试工具和固定种子清单；
- 四个官方case的统一回归入口；
- EQY、资源、时间、内存汇总报告；
- 失败样本归档规则。

C 完成标准：在Pass尚未完成时，测试框架能够对“未触发/桩触发”运行；接入真实Pass后无需改测试语义，只替换被测程序。

## 5. 共享文件与修改权限

建议逻辑目录如下，最终放入中央仓库后保持职责隔离：

```text
pmux_opt/
  include/       共享接口；B维护，变更需A/B/C共同确认
  analyzer/      A独占主责
  pass/          B独占主责
  tests/         C独占主责
  scripts/       C主责；涉及构建接入部分由B评审
  reports/       C生成，其他人只读
```

规则：

1. 三人不得同时直接修改同一文件。
2. 共享接口变更必须先改本文，再由 B 修改接口文件，A 和 C 明确确认。
3. A 不直接修改 `pass/`；B 不把证明逻辑复制进 `pass/`；C 不为了让测试通过而改生产代码。
4. 每次合并只包含一个职责内的可审查变化，禁止混入格式化或无关清理。
5. 所有失败必须保留证据，不允许只口头报告“跑过”。

具体仓库命令、双基准哈希、版本核验、阅读确认和三机基线判定见 `docs/design/M0三人协作启动检查清单.md`。

- 确定唯一中央 Git 仓库和基准提交；
- 建立 A、B、C 三条分支；
- 确认精确 Yosys 0.69 提交 `9f75ca1f9834a39a863915b5dae0c7b1e33533bc`；
- 冻结本文接口、日志字段和目录所有权；
- 运行一次未经修改的四 case 基线，确认环境一致。

M0 未完成前，不允许提交生产代码。

### M1：真正并行开发

- A：实现证明引擎及规则级验证；
- B：使用分析器桩实现枚举、计划和原子提交；
- C：完成16类测试框架、随机生成器和官方回归框架。

三人每天只同步接口变化、阻塞和可复现失败，不同步未经验证的算法猜测。

### M2：首次集成

1. B 先合入 C 的测试框架，确认桩模式可运行；
2. B 再接入 A 的真实分析器；
3. 先跑16类微型测试，不立即跑官方case；
4. 微型测试全部通过后运行100例随机回归；
5. 出现错误时按“分析结论错误→A、计划/提交错误→B、测试或环境错误→C”分派，不能多人同时修改同一问题。

### M3：G3验收

- 运行1000例固定种子随机回归；
- 运行四个官方case和ABC9；
- 执行全部结构自检与EQY；
- 形成G3报告，对照七项门槛逐项判定。

## 7. 每日同步格式

每人只报告以下内容：

```text
昨日交付：可定位到提交或文件
今日目标：一个可验证结果
当前阻塞：复现命令、输入和错误
接口变更：无 / 提案编号
测试状态：通过数、失败数、未运行数
```

“基本完成”“应该没问题”“稍后一起调”不算有效状态。

## 8. G3最终判定

只有以下条件全部满足，R1′才进入默认综合流程：

1. 16类微型测试全部通过；
2. 至少1000个固定种子随机设计全部通过EQY；
3. 四个官方case全部通过EQY；
4. 四个case均无LUT增加，且至少一个case减少；
5. DFF、IO等非目标资源不增加；
6. CPU时间和峰值内存记录完整；
7. 不存在名称或源码位置硬编码。

若只实现了预期位替换但没有LUT收益，结论必须写为“R1′功能实现正确，但未通过评分收益门”，不得扩大宣传，也不得直接加入更激进规则绕过本阶段复盘。
